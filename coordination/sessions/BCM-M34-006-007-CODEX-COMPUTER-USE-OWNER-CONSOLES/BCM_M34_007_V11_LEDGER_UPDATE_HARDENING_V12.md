1. **Journal UPDATE owner/payload bypass:** a valid verified `store_grant_journal` row for account A can be UPDATEd to account B, a different product/kind or a different `grant_payload_json`, because its verified-match trigger fires only on INSERT. Ensure a previously accepted grant's immutable owner/platform/transaction/product/kind and trusted payload cannot be rewritten by later updates. Require exactly matching verified purchase for transitions that apply grants. Do not block legitimate `pending → applied` when purchase is still verified, or `pending/applied → reversed` when parent has since been refunded.
2. **Entitlement reactivation:** after a legitimate parent `store_purchase_history.state: verified → refunded/revoked/expired` cascades `store_entitlements.state: active → revoked/expired`, a naked `UPDATE store_entitlements SET state='active'` currently bypasses the owner-match trigger. Prevent reactivation without a new, authentic matching verified purchase. Define allowed state transitions explicitly, including idempotent revocation, while retaining valid non-consumable restores.
3. **Purchase identity and refund transition mutation:** existing `store_purchase_history` owner/product/kind/application/environment and transaction binding must not silently mutate after verification; refunded/revoked/expired must not flip back to verified without an explicit trusted independent provider verification workflow (which does **not** exist now).
